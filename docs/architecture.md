# Architecture

The headset runs the Unity client. A Python server on a PC does the heavy work. They talk over one WebSocket (port 8765), normally over a private Tailscale network.

## Turn flow

1. The user holds push-to-talk and answers. The client records the audio and sends it as one `audio_data` message.
2. The server moves the session to `LISTENING`, then sends the audio to the speech-to-text worker (faster-whisper, large-v3-turbo, HTTP on port 8770). If the worker is down, the server falls back to a built-in speech-to-text service.
3. The transcript goes to the interviewer language model. By default this is Claude Haiku 5.5 through the Anthropic API. If the API call fails or gives no text, the reply is generated by the local Ollama model (qwen2.5:7b-instruct). A per-run spending cap also switches the hosted model off.
4. The reply is streamed. The server splits it after the first sentence so the voice can start early, and synthesises the rest while the first part plays.
5. Each piece goes to the Kokoro text-to-speech worker (HTTP on port 8771). If it fails, the server falls back to AllTalk (XTTS).
6. Each audio chunk is sent to the headset as soon as it exists. Rhubarb then analyses the same chunk and the mouth-shape cues follow in a separate message.
7. The client plays the chunk, drives the mouth from the cues, and sends `playback_complete` when done.

## Message contract

All messages are JSON text frames with a `type` field. Most carry a `session_id`.

Client to server:

| type | fields | purpose |
|---|---|---|
| `audio_data` | `data` (base64 audio) | the user's recorded answer |
| `control` | `action`: `begin`, `stop`, `reset`, `coach`, `timeout`, `start`, `ping` (`say` is for tests only) | session control |
| `playback_complete` | `session_id` | the headset finished playing a reply |
| `client_capabilities` | `capabilities` | what the headset supports |
| `streaming_status` | `status`: started, failed, completed | audio streaming state |
| `ping` | | keep-alive |

`control` with `action: "begin"` can also carry `job` (the job id), `interviewer` (name) and `voice`. The server uses them to pick the scenario and the matching voice. `reset` saves the finished interview before clearing the session.

Server to client:

| type | fields | purpose |
|---|---|---|
| `state_update` | state, message | session state changes (for example IDLE, LISTENING, WAITING, ERROR) |
| `audio_response` | `format: "wav"`, `data` (base64), `seq`, `more`, `text` | one chunk of the interviewer's voice |
| `visemes` | `seq`, `cues` | mouth shapes for the chunk with the same `seq` |
| `text_response` | `text` | the reply as text |
| `export_saved` | `filename`, `questions` | the interview was written to disk |
| `coach_progress` | `done`, `total` | coach review progress |
| `coach_report` | `summary`, `strengths`, `focus`, `items`, `filename` (or `error`) | the coach's feedback |
| `heartbeat`, `pong`, `error`, `system_message` | | housekeeping |

Chunk rules:

- `seq` numbers the audio chunks of a reply.
- `more: true` means another chunk of the same reply follows.
- `visemes` is keyed by `seq`. Each cue is `{"s": start, "e": end, "v": shape}` with shapes `A` to `H` and `X` (rest).

## Coach

The coach is a separate step. When an interview ends, the server saves an export (Markdown and JSON) and remembers it. When the headset sends `control: coach`, the server reviews each answer with a language model, reports progress with `coach_progress`, writes the coach notes into the same export file, and sends `coach_report`.

## Where things are

- `server/server.py`: entry point.
- `server/app/websocket/server_enhanced_fixed.py`: WebSocket handler and turn pipeline.
- `server/app/websocket/protocol.py`: message encoding and validation.
- `server/app/state/`: session and state manager.
- `server/app/lipsync.py`: Rhubarb wrapper.
- `server/app/interview_review.py`, `server/app/coach_v2.py`: export and coach.
- `server/services/llm/`: interviewer logic, Anthropic backend, job scenarios and question bank.
- `server/services/audio/`: speech-to-text and text-to-speech clients.
- `server/tools/stt_worker.py`, `server/tools/tts_worker.py`: the two GPU workers.
- `client/WebSocketManager.cs`, `client/InterviewFlow.cs`: client connection and interview flow.
